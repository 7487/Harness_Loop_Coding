# /review — 代码审查

> 对当前变更（或指定文件）进行多维度代码审查，输出结构化问题清单。

**输入**: `$ARGUMENTS`（可选：指定文件路径或 git ref，留空则审查所有未提交变更）

---

## 执行步骤

### Step 1：确定审查范围

根据 `$ARGUMENTS` 决定审查范围：

- **留空** → 运行 `git diff HEAD`，审查所有未提交的变更（staged + unstaged）
- **文件路径**（如 `src/foo.py`）→ 只审查该文件
- **git ref**（如 `main..HEAD` 或某个 commit hash）→ 审查该范围内的提交

读取 `CLAUDE.md` 中的编码规范、安全守则、性能意识部分，作为审查基准。

### Step 2：读取变更内容

读取所有需要审查的文件内容（完整文件，不只看 diff），理解：
- 文件在项目中的职责
- 变更的意图
- 上下文依赖关系

**如果涉及数据库操作**，同时读取 `docs/DB_SCHEMA.md`（如存在）。
**如果涉及 API 接口**，同时读取 `docs/API_SPEC.md`（如存在）。

### Step 3：多维度审查

对每个变更文件，逐一检查以下维度：

#### 🔴 P0 — 阻塞发布（必须修复）

- **安全漏洞**：
  - SQL 注入（字符串拼接 SQL）
  - XSS（未转义输出）
  - 硬编码密钥 / Token / Password
  - 命令注入（shell 调用未转义输入）
  - 路径遍历（未校验的文件路径）
- **数据完整性**：
  - 缺失事务保护的多步写入
  - 竞态条件（race condition）
  - 未处理的异常导致数据损坏
- **明显逻辑错误**：
  - 条件永远为真/假
  - 无限循环
  - 空指针 / None 解引用未防护

#### 🟠 P1 — 重要问题（强烈建议修复）

- **性能问题**：
  - N+1 查询
  - 循环内调用外部 API / 数据库
  - 大数据集一次性加载到内存
  - 缺少必要索引（涉及 WHERE/JOIN/ORDER BY 字段）
- **错误处理缺失**：
  - 未捕获的异常在系统边界
  - 错误信息泄露内部细节（堆栈、SQL、路径）
  - 忽略错误返回值
- **资源泄露**：
  - 文件 / 连接 / 锁未关闭
  - 上下文管理器（with / try-finally）未使用

#### 🟡 P2 — 改进建议（建议修复）

- **代码规范**：
  - 函数超过 50 行
  - 嵌套超过 4 层
  - 单文件超过 800 行
  - 硬编码魔法数字 / URL / 字符串
- **可读性**：
  - 命名不清晰（单字母变量、无意义缩写）
  - 复杂逻辑缺少注释
  - 函数职责不单一
- **DRY 违反**：
  - 3 次以上重复代码块可提取为函数
  - 重复的校验逻辑可统一

#### 🔵 P3 — 测试覆盖（评估）

- 新增的公共函数 / API 是否有对应测试
- 关键业务逻辑是否覆盖边界场景（空值、越界、并发）
- 已有测试是否需要更新以反映变更

### Step 4：输出审查报告

按以下格式输出结构化报告：

```

**审查范围**: {文件列表或 git ref}
```

### Step 5：可选 — 自动生成 bug_fix 工单

如果发现 P0 问题，询问用户是否自动生成 `bug_fix/{issue_title}.md` 工单，以便 `/execute` 优先处理。

---

## 规则

- P0 问题必须列出具体文件和行号，不允许模糊描述
- 每个问题必须给出可操作的修复建议
- 不要只列问题，要解释为什么是问题
- 如果变更质量很好，明确说明"无重大问题"，给出正向反馈
- 不要审查没有变更的文件
- 如果 `$ARGUMENTS` 指向不存在的文件或 ref，提示用户并停止
